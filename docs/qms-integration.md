# Интеграция с модулем СМК портала

Состояние на 2026-10-14. Документ для команды портала: как бэкенд портала открывает
документы СМК в редакторе и получает данные рецензирования. Бизнес-логика модуля
(статусы, маршрут Camunda, кодировка, ЭЦП, ознакомление, SLA) остаётся на портале;
Officier отвечает за редактор и за то, что редактор позволяет каждому участнику.

```text
браузер портала ── api.js + подписанный config ──> Officier (DocumentServer, :8080)
      ^                                                   |  скачивает DOCX, шлёт callback
      | config                                            v
бэкенд портала ── Bearer GATEWAY_API_KEY ──> QMS gateway (:8081)
```

Браузер никогда не обращается к шлюзу и не знает `JWT_SECRET`. Права лежат в подписанном
токене: изменённый в браузере config сервер отклоняет с ошибкой `-23` (проверено в
`docker/smoke/qms.mjs`).

## Запуск

```sh
cp .env.example .env   # заполнить JWT_SECRET, GATEWAY_API_KEY, OFFICIER_PUBLIC_URL
docker compose up -d --build
```

Демо-стенд для показа (условный портал: выбор документа, статуса, пользователя и роли,
отчёт рецензирования; без входа и проверок, не для прода):

```sh
docker compose --profile demo up -d --build   # http://127.0.0.1:8090
```

`OFFICIER_PUBLIC_URL` — адрес сервера документов, как его видит браузер. Сервер документов
должен иметь сетевой доступ к адресам файлов и callback портала; для внутренней сети
включён `ALLOW_PRIVATE_IP_ADDRESS` (сервер скачивает только URL из подписанных config).

## POST /api/v1/editor-config

Портал вызывает при каждом открытии документа, после своей проверки видимости (разд. 2 логики).

```json
{
  "document": {
    "id": "8f0c…", "versionNo": 2, "revision": "etag-или-updatedAt-файла",
    "title": "РЕГ-ДОТиОС-2026-014.docx",
    "url": "https://portal/qms/files/…", "callbackUrl": "https://portal/qms/editor/callback"
  },
  "user": {"id": "u-101", "name": "Иванов И. И.", "lang": "ru"},
  "access": {"status": "ON_REVIEW", "role": "REVIEWER", "round": 2, "stageNo": 1}
}
```

- `revision` меняется, когда сессия редактирования завершилась с изменениями (callback со
  статусом 2) или файл заменили вне редактора. От него зависит ключ документа: все участники
  одного файла попадают в одну сессию совместной работы, а новый файл открывается с новым ключом.
- `callbackUrl` обязателен, если пользователь может что-то менять; портал обрабатывает его как
  обычный callback ONLYOFFICE: статус 2 — сохранить файл и обновить `revision`; статус 6
  (принудительное сохранение во время работы) — сохранить файл, `revision` не менять, иначе
  следующий вошедший попадёт в отдельную сессию.
- `lang: "kk"` — интерфейс редактора на русском (казахского перевода нет), региональные
  настройки и проверка орфографии `kk-KZ`.

Ответ: `config` (передать в `new DocsAPI.DocEditor(id, config)`), `apiUrl` (подключить
скриптом), `policy` (`mode`, `stamp`, `readOnly`, `reviewVisible` — для интерфейса портала).

```html
<script src="{apiUrl}"></script>
<script>new DocsAPI.DocEditor('qms-editor', response.config);</script>
```

### Роли и режимы

`role` — роль пользователя именно в этом документе сейчас:
`OWNER` (владелец/автор), `REVIEWER` (участник текущего этапа `REVIEW`/`NORM_CONTROL`),
`SIGNER` (подписант этапа `APPROVE`), `SUPERVISOR` (администратор СМК, нормоконтролёр вне
маршрута, аудитор), `READER` (сотрудник области применения).

| Статус | OWNER | REVIEWER | SIGNER | SUPERVISOR | READER |
| --- | --- | --- | --- | --- | --- |
| `DRAFT` | `EDIT` | просмотр | просмотр | просмотр | отказ 403 |
| `ON_REVIEW` | `COMMENT` | `REVIEW` | просмотр | просмотр | отказ 403 |
| `ON_APPROVAL` | `COMMENT` | просмотр | `REVIEW` | просмотр | отказ 403 |
| `RETURNED` | `DECIDE` | просмотр | просмотр | просмотр | отказ 403 |
| `ACTIVE`, `ON_REVISION`, `ARCHIVED`, `CANCELLED` | просмотр | просмотр | просмотр | просмотр | просмотр без рецензирования |

- `EDIT` — свободная правка черновика.
- `REVIEW` — согласующий на своём этапе и подписант на этапе утверждения: любая правка сохраняется
  как предложенная (режим отслеживания изменений принудителен), принять или отклонить нельзя;
  комментарии. Для `REVIEWER` и `SIGNER` обязательны `round` и `stageNo`.
- `COMMENT` — автор, пока документ на маршруте (согласование и утверждение): отвечает на
  комментарии, текст не меняет.
- `DECIDE` — автор после возврата: дорабатывает текст и решает по каждой правке в панели
  «Рецензирование» (изменения от 2026-10-14). Кнопки «Принять» / «Отклонить» стоят у каждой правки.
  Отклонение без обоснования невозможно, принятие допускает комментарий (разд. 5.4). Штатные кнопки
  принятия правок редактора в этом режиме выключены (`permissions.review: false`), чтобы решение
  нельзя было принять в обход обоснования. Подробнее — «Решения автора по правкам» ниже.
- Просмотр для `READER`: комментарии и пометки рецензирования скрыты.
- Пока документ на маршруте (`ON_REVIEW`, `ON_APPROVAL`, `RETURNED`), всем, кроме `READER`, вместе
  с документом открывается панель «Рецензирование» (плагин `docker/plugins/qms-review`): по каждому
  автору — цвет его правок в тексте, ФИО, круг и этап, все правки (что вставлено, удалено,
  переоформлено, когда, в каком абзаце; клик переходит к правке) и все комментарии с ответами.
  Список обновляется по ходу работы, без сохранения. Где пользователь может менять текст
  (`REVIEW`, `DECIDE`), панель справа, а слева открыта штатная панель комментариев для ответов;
  в режимах «только комментарии» и просмотра правой панели у редактора нет, панель открывается слева.
  Вкладка «Плагины» и внешний магазин плагинов скрыты.
- Блокировка фрагмента: согласующий или подписант выделяет текст и нажимает в панели
  «Заблокировать выделенное». Фрагмент становится элементом управления содержимым с блокировкой
  `sdtContentLocked` (её соблюдает и MS Word) и заголовком «Заблокировано: ФИО (круг, этап)»;
  в правках это не отражается. Изменить заблокированный текст не может никто; снять блокировку
  может автор в режимах `EDIT` и `DECIDE` (кнопка «Снять» в панели), а согласующий — только свою.
  Настройки элементов управления в интерфейсе редактора доступны только автору
  (`permissions.modifyContentControl`), поэтому чужую блокировку не снять и через меню.
  Блокировки остаются в DOCX и переходят в следующие круги; при фиксации перед утверждением
  (`/api/v1/finalize`) они снимаются, текст остаётся (список — в отчёте рецензирования, поле `locks`).
- Во всех режимах комментарии и ответы нельзя изменить или удалить никому (ошибочный комментарий
  закрывается новым ответом), чат выключен, защита документа паролем недоступна.
- Редактируется только DOCX-исходник; PDF и приложения всегда открываются на просмотр.

Проверки «действие не тем участником» и «правка действующего документа» (`QMS-403-ROUTE`,
`QMS-423-ACTIVE-EDIT`) остаются на портале: шлюз не открывает лишних прав, но и не знает маршрута.

Подписант может оставить предложения и комментарии, поэтому перед подписанием портал проверяет
отчёт: при `openSuggestions > 0` подписание недоступно, остаётся «Вернуть с замечаниями»
(правки разбирает автор в `RETURNED`). Итоговый PDF и хэш формируются из файла без открытых правок.

### Метка круга и этапа

Каждая правка и каждый комментарий в DOCX подписаны автором с меткой: `R2.S1` (круг 2, этап 1 —
согласования или утверждения) или `R2.OWNER` (автор документа). В интерфейсе редактора показывается только ФИО. Кроме того,
редактор сохраняет идентификатор пользователя портала (`user.id`) в правках (`oouserid`) и в
`people.xml`, поэтому отчёт связывает правку с конкретным сотрудником, а не только с ФИО.

## POST /api/v1/review/report

Тело — DOCX (`application/octet-stream`) или JSON `{"url": "…"}` (например, URL из callback).
Ответ:

```json
{
  "suggestions": [{
    "id": "4c1d…", "type": "REPLACE",
    "author": {"name": "Петров П. П.", "userId": "u-201", "stamp": "R1.S2", "round": 1, "stageNo": 2, "role": "PARTICIPANT"},
    "date": "2026-10-13T09:05:00Z", "textBefore": "старый", "textAfter": "новый",
    "anchor": {"part": "word/document.xml", "paragraph": 1, "context": "Срок: новый порядок."}
  }],
  "comments": [{"id": "0", "parentId": null, "author": {…}, "date": "…", "text": "Уточнить область",
                "resolved": false, "anchorText": "область применения"}],
  "summary": {"openSuggestions": 5, "comments": 2, "threads": 1, "unresolvedThreads": 1,
              "byStamp": {"R1.S1": {"suggestions": 3, "comments": 1}}}
}
```

- `locks`: заблокированные фрагменты — `userId`, `name`, `stamp`, `round`, `stageNo`, `text`,
  `contentLocked`; число — в `summary.locks`.
- `type`: `INSERT`, `DELETE`, `REPLACE` (как в `QmsSuggestion`) и `FORMAT` (изменение оформления).
  Учитываются основной текст, колонтитулы и сноски.
- Всё, что есть в файле, — правки без решения. Принятые и отклонённые правки из DOCX исчезают,
  поэтому историю (`QmsSuggestion`, `QmsComment`) портал ведёт сам: сохраняет отчёт после каждого
  callback 2/6. `id` правки стабилен, пока правка в файле, — по нему сравниваются соседние отчёты.
- `summary.openSuggestions > 0` — основание для `QMS-409-OPEN-SUGGESTIONS` при повторной отправке
  и для запрета перехода к `APPROVE` (разд. 5, п. 6 и 8).
- `comments[].document: true` — комментарий ко всему документу, а не к фрагменту (редактор хранит
  такие в `word/commentsDocument.xml`; их `id` с префиксом `doc-`). Так записываются решения автора.

### Решения автора по правкам

Изменения от 2026-10-14 (разд. 5.4). Решение автора в режиме `DECIDE` панель записывает в сам
документ комментарием ко всему документу. Он неизменяемый, как все комментарии, переживает
исчезновение правки из текста и виден всем участникам маршрута: в панели «Решения автора» и в
комментариях редактора. Формат строгий, его разбирает шлюз:

```text
Правка отклонена.
Автор правки: Петров П. П. (круг 1 · этап 2), 2026-10-13T09:05:12Z
Вставлено: «срочно»
Обоснование: термин уже определён в п. 1.2
```

В отчёте — `decisions` по времени решения и `summary.decisions` (`accepted`, `rejected`):

```json
{"commentId": "doc-0", "decision": "REJECTED", "reason": "термин уже определён в п. 1.2",
 "decidedBy": {"name": "Сидорова А. А.", "userId": "u-100", "stamp": "R1.OWNER", …}, "decidedAt": "2026-10-14T10:00:00Z",
 "suggestion": {"author": {"name": "Петров П. П.", "stamp": "R1.S2", "round": 1, "stageNo": 2},
                "date": "2026-10-13T09:05:12Z", "type": "INSERT", "textBefore": "", "textAfter": "срочно", "changes": […]}}
```

- `reason` — обоснование отклонения или комментарий к принятию (`decisionReason` в `QmsSuggestion`);
  `decidedBy`/`decidedAt` — `decidedBy`/`decidedAt`.
- Правка из прошлого отчёта сопоставляется с решением по автору (`stamp`, имя), `date` и тексту
  (`type`, `textBefore`, `textAfter`): одна правка рецензента часто совпадает с другой по секунде.
- Решением считается только комментарий с меткой автора документа (`R…OWNER`); такой же текст от
  другого участника — обычный комментарий.
- Автор правки получает уведомление о решении от портала: по появлению записи в `decisions`.

Автор в `DECIDE` правит текст свободно и может стереть или перепечатать правку рецензента напрямую.
Панель это замечает («Правки исчезли без решения») и просит отменить действие или оформить решение;
оформленное решение записывается так же. Если документ всё же сохранён с исчезнувшей правкой без
решения (правка была в прошлом отчёте, её нет ни в `suggestions`, ни в `decisions`), портал
показывает это автору и не даёт отправить документ на новый круг, пока решение не оформлено.

## POST /api/v1/editor/close

Изменения от 2026-10-14. Портал вызывает при **каждой смене статуса или этапа** документа
(отправка на согласование, переход к следующему этапу, возврат, переход к утверждению):
у всех, кто открыл документ, редактор отключается, и права прежнего статуса пропадают.

```json
{"document": {"id": "8f0c…", "versionNo": 2, "revision": "etag-7"}}
```

`id`, `versionNo`, `revision` — те же, что при открытии (из них считается ключ сессии).
Ответ: `{"key": "qms_…", "session": "closing", "users": ["u-1011"]}` или `{"session": "none"}`.

- `closing` — сессия была. Сервер документов сохраняет её и присылает на `callbackUrl` обычный
  callback: **2** — были изменения (сохранить файл, сменить `revision`), **4** — изменений не было.
  Это и есть событие «документ сохранён» для Camunda вместо паузы 60 с (разрыв 9 схемы): процесс
  ждёт callback 2 или 4 этого документа. Перед ним может прийти callback 1 с `userdata: "qms-close"`.
- `none` — сервер документов эту версию не знает: сохранённый файл портала уже окончательный.
- Отключённый пользователь видит сообщение редактора о закрытии документа; продолжить в старой вкладке
  нельзя. Открыв документ заново, он получит конфигурацию по новому статусу.

Если callback не пришёл за 1–2 минуты, повторите вызов: при `none` или `users: []` сессии уже нет.

## POST /api/v1/finalize

Изменения от 2026-10-14. Фиксация перед этапом `APPROVE` (разд. 6.1): после закрытия сессии
портал передаёт окончательный DOCX и данные для листа согласования.

```json
{
  "document": {
    "url": "https://portal/qms/files/…",
    "code": "РЕГ-ДОТиОС-2026-014", "name": "Регламент управления документацией СМК", "versionNo": 2
  },
  "approvals": [
    {"name": "Иванов И. И.", "position": "Начальник ОТиОС", "stage": "Согласование, этап 1",
     "decision": "Согласовано", "date": "2026-10-13T09:00:00Z"},
    {"name": "Ахметова Г. К.", "position": "Нормоконтролёр", "stage": "Нормоконтроль",
     "decision": "Согласовано с замечаниями", "comment": "Замечания учтены", "date": "2026-10-14"}
  ],
  "options": {"keepComments": false, "keepLocks": false}
}
```

- Источник файла — `document.url` (шлюз скачивает сам) или `document.base64`, ровно одно из двух.
- Если в файле есть правки без решения, ответ `409 GW-409-OPEN-SUGGESTIONS`:
  `details.openSuggestions` — сколько, `details.suggestions` — первые 20. Подписание недоступно,
  документ возвращается автору (разд. 5.8).
- Ответ `200`:

```json
{
  "source": {"sha256": "…", "size": 48211, "base64": "…"},
  "pdf": {"sha256": "…", "size": 81351, "base64": "…"},
  "removed": {"comments": 3, "locks": 1, "emptyInsertions": 0},
  "review": {"suggestions": [], "comments": [ … ], "locks": [ … ], "summary": { … }}
}
```

- `source` — замороженный исходник: текст без изменений, но без комментариев (в редакторе они
  неудаляемые и иначе перешли бы в следующую редакцию), без блокировок фрагментов и без пустых
  служебных правок. Именно его копирует пересмотр в `versionNo + 1`. `keepComments` и `keepLocks`
  оставляют их, если портал решит иначе.
- `pdf` — то, что подписывает утверждающий: текст и последней страницей лист согласования (код,
  наименование, редакция, таблица № / ФИО / должность / этап / решение с комментарием / дата и
  SHA-256 исходника). Даты печатаются по `QMS_TIME_ZONE` (по умолчанию `Asia/Almaty`).
- `review` — отчёт рецензирования по файлу до очистки: окончательный журнал комментариев для
  `QmsComment`.
- Хэш PDF портал сохраняет и сверяет с подписанным файлом (разд. 6.2). Ошибка конвертации —
  `502 GW-502-PDF` (для пользователя `QMS-502-PDF`).
- Замороженный исходник и PDF портал хранит отдельно от рабочего файла. Подписант на `ON_APPROVAL`
  открывает рабочий файл в режиме рецензирования; если он оставил правки (`openSuggestions > 0`
  в отчёте), остаётся только «Вернуть с замечаниями», и PDF удаляется (разд. 4).

PDF строит сервер документов: шлюз отдаёт ему копию для печати по одноразовой ссылке
`GATEWAY_INTERNAL_URL/files/…` (без ключа, только на время конвертации). В compose адреса заданы:
`OFFICIER_INTERNAL_URL=http://officier`, `GATEWAY_INTERNAL_URL=http://qms-gateway:8081`.

## Что ещё не сделано

- Отзыв правки рецензентом (`WITHDRAWN`): рецензент может удалить свою правку штатно, но отдельной
  отметки об отзыве нет; портал видит только исчезновение правки до решения автора.
- Сообщения об ошибках шлюза (`GW-…`) — технические; тексты для пользователя RU/KZ формирует портал.
