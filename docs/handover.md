# Officier 0.2.0 — передача разработчику портала

Документ для разработчика корпоративного портала: как заменить текущий сервер документов
(ONLYOFFICE Document Server, к которому портал обращается напрямую) на Officier и сервис
`qms-gateway` модуля СМК. Состояние на 2026-10-14.

Подробный справочник API — [docs/qms-integration.md](docs/qms-integration.md), устройство и
настройка контейнера — [docs/container.md](docs/container.md). В пакете поставки эти файлы лежат
в папке `docs/`.

## 1. Что меняется

Было: бэкенд портала сам собирает конфигурацию редактора, подписывает её JWT, принимает callback,
а процесс Camunda после правок ждёт 60 секунд и конвертирует DOCX в PDF.

Стало:

```text
браузер ── api.js + подписанная конфигурация ──> Officier (сервер документов, HTTPS)
   ^                                                  │  скачивает DOCX, шлёт callback (как раньше)
   │ конфигурация                                     v
бэкенд портала ── Bearer GATEWAY_API_KEY ──> qms-gateway ── Command API, PDF ──> Officier
```

- Officier — сервер документов на базе ONLYOFFICE Docs 9.4.0 Community: тот же `api.js`, тот же
  формат callback, тот же DOCX. Логотипы и ссылки ONLYOFFICE убраны, интерфейс на русском.
- `qms-gateway` — небольшой сервис (Node.js 22, без зависимостей). Бэкенд портала вызывает его
  вместо того, чтобы самому собирать конфигурацию. Шлюз знает правила модуля СМК: какой режим
  редактора дать по статусу документа и роли пользователя.

Что получает модуль СМК (разделы описания «Модуль СМК логика работы»):

| Возможность | Раздел |
| --- | --- |
| Режим редактора по статусу и роли: черновик, рецензирование, только комментарии, доработка, просмотр | 2, 5 |
| Правки и комментарии подписаны автором, кругом и этапом (`R2.S1`); комментарии нельзя изменить или удалить | 5.1, 5.7 |
| Панель «Рецензирование»: кто что исправил и прокомментировал — сразу, без нажатий | 5.3 |
| Блокировка фрагмента согласующим: менять может только автор документа | — |
| Решения автора по правкам: отклонение только с обоснованием, решения записываются в документ | 5.4 |
| Отчёт рецензирования из DOCX: правки, комментарии, блокировки, решения — для `QmsSuggestion`, `QmsComment` | 5 |
| Закрытие сеансов при смене статуса; событие «документ сохранён» вместо паузы 60 с | 4, разрыв 9 схемы |
| Фиксация перед утверждением: исходник без служебных пометок, PDF с листом согласования, SHA-256 | 6.1 |
| Одновременная работа: совместное редактирование в реальном времени, параллельная конвертация | — |

`/welcome/officier-build.json` на работающем сервере и в метке `org.opencontainers.image.revision`.

## 3. Сервер и сеть

**Сервер:** Linux x86_64, Docker 24+ с Compose v2. Место: около 7 ГБ под образы плюс тома.

**Ёмкость.** Ограничено число **разных документов**, одновременно открытых на редактирование.
Пользователи в уже открытом документе и просмотр в лимит не входят. Масштабирование только
вертикальное (Community: один экземпляр, сеансы в памяти процесса).

| Память | Документов на редактирование | Рекомендация |
| --- | --- | --- |
| 8 ГБ | ~235 | минимум для эксплуатации, 4 ядра |
| 16 ГБ | ~480 | основной вариант, 8 ядер |
| 32 ГБ | ~970 | при росте числа документов |

Ядра определяют скорость открытия, сохранения и формирования PDF: одна конвертация занимает 2–3
ядра. Подробнее — раздел «Производительность и ёмкость» в `docs/container.md`.

**Сетевые потоки:**

| Откуда | Куда | Зачем |
| --- | --- | --- |
| Браузеры пользователей | `https://<сервер документов>` (443, прокси → порт 8080) | редактор, WebSocket совместной работы |
| Бэкенд портала | `http://<сервер>:8081` (шлюз) | конфигурации, отчёты, закрытие сеансов, фиксация |
| Сервер документов | адреса файлов портала (`document.url`) | скачивание DOCX |
| Сервер документов | `callbackUrl` портала | сохранения (callback) |
| Шлюз | сервер документов (внутри compose) | Command API, конвертация в PDF |

- Шлюз не должен быть доступен из браузеров: только из сети бэкенда портала (`GATEWAY_BIND`).
- Доступ в интернет при работе не нужен: шрифты собраны в образе, магазин плагинов выключен.
- Сервер документов скачивает только адреса из подписанных конфигураций; приватные адреса
  разрешены (`ALLOW_PRIVATE_IP_ADDRESS=true`), потому что портал во внутренней сети.

## 4. Установка

Быстрый путь — установщик `officier-install.sh` из релиза (в репозитории `deploy/install.sh`). Он
проверит сервер, сверит контрольные суммы, загрузит образы, создаст `.env` со случайными секретами,
запустит сервисы и проверит, что сервер документов отвечает, а шлюз выдаёт подписанные конфигурации.
Повторный запуск с пакетом новой версии обновляет образы, секреты сохраняются.

```sh
tar -xf officier-0.2.0-package.tar && cd officier-0.2.0
sudo bash ../officier-install.sh --public-url https://docs.<домен> --gateway-bind <внутренний IP>
# установка в /opt/officier, ключ шлюза и JWT_SECRET — в /opt/officier/.env
```

Вручную то же самое:

```sh
sha256sum -c SHA256SUMS
docker load -i images/officier-0.2.0.tar.gz
docker load -i images/officier-qms-gateway-0.2.0.tar.gz
# при своём реестре: docker tag/push и указать OFFICIER_IMAGE, OFFICIER_GATEWAY_IMAGE в .env

cd deploy
cp .env.example .env
chmod 600 .env
# заполнить .env:
#   JWT_SECRET=<openssl rand -hex 32>        новый, не от текущего сервера
#   GATEWAY_API_KEY=<openssl rand -hex 32>
#   OFFICIER_PUBLIC_URL=https://docs.<домен>  как адрес видят браузеры
#   GATEWAY_BIND=<внутренний IP>              интерфейс для бэкенда портала
docker compose up -d
docker compose ps        # оба сервиса healthy
```

HTTPS: пример для nginx — `deploy/nginx-officier.conf` (WebSocket, заголовки `X-Forwarded-*`,
длинные тайм-ауты). Подставьте имя сервера и сертификат.

Проверка после запуска:

```sh
curl -s https://docs.<домен>/healthcheck                         # true
curl -s http://<шлюз>:8081/healthz                               # {"ok":true}
curl -s https://docs.<домен>/welcome/officier.html               # правовая страница
curl -sI https://docs.<домен>/welcome/officier-source.tar.gz      # исходники, 200
curl -s -X POST http://<шлюз>:8081/api/v1/editor-config \
  -H "Authorization: Bearer $GATEWAY_API_KEY" -H 'Content-Type: application/json' \
  -d '{"document":{"id":"check","versionNo":1,"revision":"1","title":"Проверка.docx","url":"https://portal/x.docx"},
       "user":{"id":"u-1","name":"Проверка"},"access":{"status":"ACTIVE","role":"READER"}}'
# в ответе config с полем token и apiUrl на https://docs.<домен>/…/api.js
```

## 5. Что поменять в портале

Рабочий пример бэкенда портала — `demo/server.js` в исходниках, около 200 строк. Он открывает
документ, принимает callback, закрывает сеансы с ожиданием сохранения и фиксирует документ.
Это демонстрация: проверки подлинности callback в нём нет.

### 5.1. Открытие документа

Вместо своей сборки конфигурации и подписи — `POST /api/v1/editor-config` (`docs/qms-integration.md`):

```json
{
  "document": {"id": "<id документа>", "versionNo": 2, "revision": "<меняется с каждым новым файлом>",
               "title": "РЕГ-ДОТиОС-2026-014.docx", "url": "<адрес DOCX для сервера документов>",
               "callbackUrl": "<callback портала>"},
  "user": {"id": "<id сотрудника>", "name": "Иванов И. И.", "lang": "ru"},
  "access": {"status": "ON_REVIEW", "role": "REVIEWER", "round": 2, "stageNo": 1}
}
```

- `role` — роль сотрудника **в этом документе сейчас**: `OWNER`, `REVIEWER` (участник текущего
  этапа согласования или нормоконтроля), `SIGNER` (утверждающий), `SUPERVISOR` (администратор СМК,
  аудитор), `READER`. Для `REVIEWER`/`SIGNER` обязательны `round` и `stageNo`.
- `revision` — версия сохранённого файла: меняется после callback со статусом 2 и при замене
  файла вне редактора, **не** меняется после статуса 6. Из `id`, `versionNo`, `revision` шлюз
  считает ключ сеанса: все пользователи одного файла попадают в один сеанс.
- Ответ: `config` передать в браузер без изменений (`new DocsAPI.DocEditor(id, config)`), скрипт
  подключить по `apiUrl`, `policy` — для интерфейса портала. Изменённая в браузере конфигурация
  отклоняется сервером (ошибка −23).
- Убрать из портала: свою подпись конфигураций, свою логику прав редактора по статусам.

### 5.2. Callback

Формат прежний (статусы 1, 2, 4, 6). Обязательно:

1. **Проверять подпись.** Сервер документов присылает `Authorization: Bearer <JWT>` (HS256,
   секрет `JWT_SECRET`, срок 5 минут). Доверять только полю `payload` проверенного токена, а не
   телу запроса. Иначе кто угодно в сети подсунет порталу чужой файл.
2. Скачивать файл только с сервера документов (хост из `OFFICIER_PUBLIC_URL` или его внутреннее
   имя), а не с любого адреса из callback.
3. Статус 2 — сохранить файл, сменить `revision`. Статус 6 — сохранить файл, `revision` не менять.
   Статус 4 — сеанс закрыт без изменений. Ответ всегда `{"error":0}`.

### 5.3. Журнал рецензирования

После каждого сохранения (2 и 6) — `POST /api/v1/review/report` с сохранённым файлом. В ответе
правки (`suggestions`), комментарии (`comments`), блокировки (`locks`) и решения автора
(`decisions`: решение, обоснование, кто и когда, какая правка). Из них портал ведёт
`QmsSuggestion`, `QmsComment`, `QmsHistory` и рассылает уведомления: автору правки — о решении.

Правка, которая была в прошлом отчёте и исчезла без записи в `decisions`, — решение не оформлено:
показать автору документа и не отправлять документ на новый круг, пока оно не оформлено.

### 5.4. Смена статуса или этапа

На **каждом** переходе (отправка на согласование, следующий этап, возврат, переход к утверждению,
утверждение):

1. `POST /api/v1/editor/close` с `{"document": {"id", "versionNo", "revision"}}`.
2. Ответ `session: "none"` — сеанса нет, сохранённый файл окончательный.
   Ответ `session: "closing"` — все пользователи отключены; ждать callback 2 или 4 этого документа
   (в Camunda — промежуточное событие-сообщение). Если его нет 1–2 минуты, повторить вызов.

Это заменяет фиксированную паузу `PT60S` в `qms_document_approval_process` (разрыв 9 схемы).
Пользователь со старой вкладкой видит, что документ закрыт, и при повторном открытии получает
права нового статуса.

### 5.5. Перед утверждением

После закрытия сеанса — `POST /api/v1/finalize`: окончательный файл (`document.url` или
`document.base64`), код, наименование, `versionNo`, список решений для листа согласования
(`approvals`: ФИО, должность, этап, решение, комментарий, дата).

- `409 GW-409-OPEN-SUGGESTIONS` — в тексте есть правки без решения: подписание недоступно (5.8).
- `200` — `source` (замороженный исходник) и `pdf` (что подписывает утверждающий) в base64 с
  SHA-256 и размером, `removed` (что убрано из исходника), `review` (окончательный журнал).
  Портал сохраняет оба файла и хэши отдельно от рабочего файла. Подписывается этот PDF;
  после подписи хэш подписанного файла сверяется с сохранённым (6.2).
- Собственную конвертацию DOCX → PDF для утверждения из процесса можно убрать.

### 5.6. Сообщения об ошибках

Шлюз отвечает `{"error": "GW-…", "message": "…", "details": …}`. Тексты для пользователей
формирует портал:

| Шлюз | Для пользователя |
| --- | --- |
| `GW-409-OPEN-SUGGESTIONS` | `QMS-409-OPEN-SUGGESTIONS` |
| `GW-502-PDF` | `QMS-502-PDF` |
| `GW-403-NOT-VISIBLE` | документ недоступен сотруднику вне маршрута |
| `GW-422-*`, `GW-401-AUTH`, `GW-502-DOCSERVER`, `GW-503-*` | техническая ошибка, в журнал |

## 6. Переключение

Документы хранятся в портале, у серверов документов общего состояния нет. Ключи сеансов
у шлюза свои (`qms_…`), поэтому старые и новые сеансы не пересекаются.

1. Развернуть Officier и шлюз рядом с текущим сервером (свои адреса), пройти проверку из раздела 7
   на тестовом документе.
2. Окно переключения: прекратить открытие документов на текущем сервере. Открытые сеансы закрыть
   его Command API (`forcesave`, затем `drop`) или дождаться их callback, убедиться, что портал
   сохранил последние файлы.
3. Переключить бэкенд портала на шлюз (адрес, `GATEWAY_API_KEY`) и включить проверку callback
   с новым `JWT_SECRET`. Адрес `api.js` браузер получает из ответа шлюза.
4. Старый сервер оставить на час для запоздавших callback, затем остановить.

Существующие DOCX открываются без преобразований. Правки и комментарии, сделанные до
переключения, в отчёте будут без метки круга и этапа (`stamp: null`).

**Откат:** вернуть настройки портала на прежний сервер. Файлы, сохранённые через Officier, — обычный
DOCX, прежний сервер их открывает.

## 7. Проверка после переключения

На тестовом документе пройти сценарий (так же устроен стенд `demo/`):

1. Автор, черновик: правит свободно.
2. Согласующий, «На согласовании»: правки только предложениями, комментарий; в панели
   «Рецензирование» видно автора, круг и этап. Выделить слово и «Заблокировать выделенное».
3. Смена статуса: `editor/close`, пришёл callback 2, `revision` сменилась.
4. Автор, «На доработке»: в панели принять одну правку и отклонить другую; без обоснования
   отклонить нельзя. Снять блокировку.
5. Отчёт рецензирования: `decisions` с обоснованием.
6. `finalize`: PDF открывается, последняя страница — лист согласования; SHA-256 совпадают.
7. Сотрудник, «Действует»: только просмотр, без пометок.

Автоматические проверки в исходниках: `cd gateway && npm test` (42 теста), сквозной сценарий в
настоящем редакторе — `docker/smoke/qms.mjs` (нужны Node 22 и Playwright, см. `docs/qms-integration.md`).

## 8. Эксплуатация

- **Перезапуск и обновление:** `docker compose up -d` / `docker compose restart officier`. При
  остановке контейнер до 2 минут сохраняет открытые документы. Несохранённые правки живут в памяти
  процесса: аварийное завершение их теряет. Обновлять в нерабочее время.
- **Обновление версии:** загрузить новые образы, поменять `OFFICIER_IMAGE`/`OFFICIER_GATEWAY_IMAGE`,
  `docker compose up -d`. Тома сохраняются.
- **Шрифты организации:** положить в том `fonts` и перезапустить контейнер; списки шрифтов
  пересобираются до старта (около 4 минут, только если набор изменился).
- **Журналы:** `docker compose logs officier qms-gateway`; шлюз пишет по строке JSON на запрос.
  Признак нехватки памяти — в журнале `forced view mode by community memory guard`: новые документы
  открываются только на просмотр, нужно больше памяти.
- **Резервные копии:** источник истины — хранилище портала. Тома (`data`, `cache`, `logs`, `fonts`)
  копировать не обязательно, кроме своих шрифтов.
- **Секреты:** `JWT_SECRET` и `GATEWAY_API_KEY` в хранилище секретов. Смена `JWT_SECRET`
  делает недействительными открытые конфигурации: пользователи открывают документы заново.

## 9. Лицензия

Officier — изменённая версия ONLYOFFICE Docs, распространяется по GNU AGPL v3 с дополнительными
условиями (`LICENSE`).

- Пользователям доступен исходный код именно этой версии: сервер раздаёт его по
  `/welcome/officier-source.tar.gz`, ссылка — в «Файл → О программе» и на `/welcome/officier.html`.
  Эту ссылку и правовую информацию убирать нельзя.
- Если вы меняете код, соберите новую поставку `scripts/package-release.sh <версия>`: она встраивает
  в образ исходники новой версии. Даты и суть изменений добавьте в `docker/branding/branding.json`
  (`legalNotice`) и `docker/welcome.html`.
- Товарный знак ONLYOFFICE в интерфейсе не используется.

## 10. Ограничения и что ещё предстоит решить

- **Нужно подтверждение заказчика:** при фиксации из исходника убираются комментарии и блокировки
  (иначе неудаляемые комментарии переходят в следующую редакцию). Журнал возвращается порталу.
  Сохранить их — `options.keepComments`, `options.keepLocks`.
- Отзыв правки рецензентом (`WITHDRAWN`) отдельно не отмечается: портал видит исчезновение правки до
  решения автора.
- Встраивание — штатное, через iframe `api.js`.
- Казахского интерфейса редактора нет: интерфейс русский, региональные настройки `kk-KZ`.
- Лист согласования имеет фиксированный вид (`gateway/src/docx.js`).
